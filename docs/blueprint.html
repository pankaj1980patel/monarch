Monarch: Native macOS Window Manager

A complete architecture and migration plan to replace the existing Hammerspoon setup with one lightweight native macOS application, preserving its shortcuts, workspaces, custom switcher, overview, auto-focus and global trackpad gestures.

Swift 6 / AppKitEvent-drivenSingle processPer-app AX queuesNo keyboard event tapSwift Package ManagerPrivate gesture API

What changed in revision 2

  • One queue per app instead of one window actor. A hung app blocks only its own queue, and multi-window operations such as a workspace switch run across apps in parallel.
  • Every Accessibility call is bounded by a 0.25 s messaging timeout (configurable), instead of macOS's default of about 6 s.
  • Window moves skip work: no move when the frame already matches; size, position, size ordering; the app's enhanced-UI mode is switched off during the move.
  • No keyboard event tap. Every shortcut, ⌘Tab included, is a Carbon hotkey. For ⌘Tab, the system's own symbolic hotkey is disabled first. This removes the Input Monitoring permission.
  • Single-window focus uses the private front-process call plus AXRaise, so only the chosen window comes forward.
  • Window IDs come from the private _AXUIElementGetWindow, looked up once per window and cached.
  • The ⌘Tab panel is built once and kept hidden. This replaces lazy creation, so the first press has no delay.
  • The switcher and overview use icons and metadata, not screenshots. No Screen Recording permission is needed, and the snapshot slide animation is dropped or captured as the gesture starts.
  • Build with Swift Package Manager and a bundling script. Xcode is optional; the Command Line Tools are enough.
  • Hammerspoon handoff protocol so both can run during migration without fighting over keys (section 10).

1. Objectives and non-negotiable requirements

  • Preserve every existing keyboard shortcut and its behavior.
  • Preserve the custom Cmd+Tab and Mission Control-style interfaces.
  • Support global three-finger and four-finger gestures.
  • Support the LG and MacBook displays with independent workspaces.
  • Minimize idle CPU, memory, allocations and event-processing overhead.
  • Avoid unnecessary background processes and polling.
  • Keep the application operational across macOS updates, isolating private gesture code.

Core rule: every feature consumes shared state. No feature independently performs full window scans.

Window state model

struct ManagedWindow: Identifiable {
    let id: CGWindowID
    let pid: pid_t

    var title: String
    var bundleID: String?

    var screenID: CGDirectDisplayID
    var workspaceID: Int

    var frame: CGRect
    var previousFrame: CGRect?

    var isMinimized: Bool
    var isVisible: Bool
    var lastFocusedAt: UInt64
}

Use stable window IDs and validate references before operations. Do not assume an AX element remains valid after its application closes.

Concurrency model

Execution domainResponsibilities
Main threadAppKit UI, panels and animations
One serial queue per appAll AX calls for that app: reads, moves, observer follow-ups. Apps run in parallel; a hung app blocks only itself.
Main actorCentral window cache, display cache, hotkey dispatch: microseconds of work, then one hop to the app queue
Input callbackDecode event, update minimal state, enqueue action

Never perform blocking Accessibility calls, window enumeration or rendering inside a CGEventTap callback. AX operations need bounded timeouts, error handling and stale-state recovery.

Observer callbacks run on the main run loop and do no AX work there: they hand off to the app's queue. Window move and resize notifications are coalesced to one frame read per 50 ms per window, so dragging a window costs almost nothing.

6. Private global gesture subsystem

Global raw three-finger and four-finger recognition while another application is active requires a separate implementation from normal AppKit gesture recognizers.

MacBook Trackpad
↓
Private MultitouchSupport API
↓
Finger count · Coordinates · Timestamps
↓
Gesture recognizer
Direction · Distance · Duration · Confidence
↓
Gesture router → Workspace / Overview

Recognition rules:

  • Track the centroid of fingers and require a consistent finger count.
  • Calculate direction and apply a minimum displacement threshold.
  • Reject noisy or incomplete gestures.
  • Trigger only once per gesture; ignore subsequent frames until all fingers lift.
  • Start with reliable directional recognition rather than complex velocity prediction.

Risk: MultitouchSupport is private and undocumented. It can change across macOS versions and creates maintenance and distribution risks. Keep it behind a dedicated interface and feature flag. Validate on the actual Mac and OS before depending on it.

Initially preserve the existing logical-workspace behavior: park windows offscreen and restore their saved frames. Each display maintains independent active workspace state and parked-window positions.

Do not switch to native macOS Spaces in the first release. Controlling Spaces reliably is more complicated and may require private APIs. Evaluate it later as an optional backend.

10. Migration strategy

  1. Build the native application alongside Hammerspoon.
  2. Implement native snapping first.
  3. Compare every shortcut and window behavior.
  4. Migrate focus, switcher and workspaces incrementally.
  5. Implement private gestures last.
  6. During testing, avoid duplicate hotkey ownership between the two systems, using the handoff protocol below.
  7. After regression tests pass, disable Hammerspoon and remove its configuration.

Keep existing .bak files and configuration as the rollback reference.

Hammerspoon handoff protocol

  1. Hammerspoon keeps a list of the keys that Monarch has taken over (v0.1: the 16 snap keys, ⌃⌥⌘ ←/→/↩ and ⌃⌘ F).
  2. Once Monarch has Accessibility and its shortcuts are registered, it posts the distributed notification dev.monarch.Monarch.active with "on". Hammerspoon then disables its own copies of those keys.
  3. When Monarch's shortcuts are turned off, or it quits, it posts "off", and Hammerspoon re-enables them. If Monarch crashes, Hammerspoon's app watcher does the same.
  4. After a Hammerspoon reload, Hammerspoon posts dev.monarch.Monarch.query, and Monarch answers with its current state.
  5. Each later step adds its keys to that list, until Hammerspoon owns nothing and can be removed.

11. Permissions and system integration

  • Accessibility: window discovery, moving and focusing windows.
  • Input Monitoring: not needed. Shortcuts are Carbon hotkeys, and the mouse tap for auto focus is listen-only (covered by Accessibility).
  • Screen Recording: only if the overview actually captures screen content. Do not request it just to draw a metadata-based native overview.
  • Login startup: SMAppService.mainApp, toggled from the menu. One application process.
  • Stable signature: macOS ties the Accessibility grant to the code signature. The build script signs with a local self-signed certificate kept in its own keychain, so the grant survives rebuilds. It falls back to ad-hoc signing until that keychain is in the user's search list.

Do not create a separate daemon unless profiling or system constraints demonstrate a need.

12. Definition of done

  • Every existing keyboard shortcut works.
  • Both displays maintain independent workspaces.
  • Window positions survive application restarts.
  • Cmd+Tab preserves global MRU behavior.
  • Only selected windows come forward.
  • Overview supports cross-screen drag-and-drop.
  • Three-finger up/down works globally.
  • Four-finger left/right works globally.
  • No duplicate event listeners after restart.
  • Sleep/wake does not break input handling.
  • Display reconnection rebuilds screen mappings.
  • No sustained CPU usage when idle.
  • No sustained memory growth.
  • Hammerspoon can be completely removed.
